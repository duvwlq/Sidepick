# React 프로젝트 구조 공유

작성일: 2026-05-01
대상: 결과 페이지 React 작업 시작 전 구조 공유

## 1. 현재 프론트엔드 스택

- React 19 + TypeScript
- Vite
- Tailwind CSS v4
- React Router DOM v7

`fe/package.json` 기준으로 별도 UI 프레임워크(MUI, Ant Design, Chakra 등)는 아직 사용하지 않고 있습니다.  
공통 UI는 내부 컴포넌트를 직접 만들어 쓰는 방식입니다.

## 2. 프로젝트 최상위 구조

프론트엔드는 `fe` 디렉터리 아래에 있습니다.

```text
fe/
  public/
  src/
    assets/
    components/
      ai-analysis/
      auth/
      common/
      experience-write/
      home/
      layout/
    constants/
    context/
    hooks/
    lib/
    pages/
      auth/
    styles/
    App.tsx
    main.tsx
  package.json
  vite.config.ts
  tailwind.config.js
```

## 3. 폴더 역할

### `src/pages`

라우트 단위 페이지 컴포넌트가 들어갑니다.

- `Home.tsx`: 메인 홈
- `Explore.tsx`: 전체 탐색
- `Create.tsx`: 실패 경험 작성 플로우
- `ExperienceDetail.tsx`: 경험 상세
- `AiAnalysisResultPage.tsx`: 결과 페이지
- `MyPage.tsx`: 마이페이지
- `pages/auth/*`: 로그인, 회원가입, 소셜 콜백

### `src/components`

페이지 안에서 재사용하는 UI 조각들입니다.

- `layout/`: 상단 헤더, 하단 탭바, 공통 레이아웃
- `common/`: 버튼, 카드, 검색바 등 범용 UI
- `auth/`: 인증 화면 전용 UI
- `experience-write/`: 글쓰기 4단계 플로우 전용 UI
- `ai-analysis/`: 결과 페이지 전용 UI
- `home/`: 홈 화면 전용 UI

### `src/lib`

API 호출과 세션 저장 로직이 있습니다.

- `api.ts`: 백엔드 API wrapper, 타입 정의 포함
- `session.ts`: access token / refresh token / user localStorage 관리

### `src/hooks`

페이지 상태를 묶는 커스텀 훅입니다.

- `useExperienceWrite.ts`: 글쓰기 step 상태와 form 상태 관리

### `src/context`

화면 간 공유해야 하는 인증 흐름 상태를 관리합니다.

- `AuthFlowContext.tsx`

### `src/constants`

선택지나 mock 데이터 같은 정적 상수를 둡니다.

## 4. 앱 진입 구조

엔트리는 아래처럼 단순합니다.

- `src/main.tsx`에서 `globals.css`를 로드
- `src/App.tsx`를 `#root`에 마운트

`App.tsx`에서 전체 라우터를 구성합니다.

```tsx
<BrowserRouter>
  <AuthFlowProvider>
    <Routes>...</Routes>
  </AuthFlowProvider>
</BrowserRouter>
```

즉, 전역 구조는 현재

1. `BrowserRouter`
2. `AuthFlowProvider`
3. `Routes`

순서입니다.

## 5. 라우팅 방식

현재는 `react-router-dom`의 기본 선언형 라우팅을 사용합니다.

```text
/                       -> Home
/auth                   -> AuthEntryPage
/login                  -> AuthEntryPage
/auth/kakao/callback    -> KakaoCallbackPage
/auth/google/callback   -> GoogleCallbackPage
/signup/email           -> SignupEmailPage
/signup/verify          -> SignupVerifyPage
/signup/password        -> SignupPasswordPage
/signup/nickname        -> SignupNicknamePage
/explore                -> Explore
/create                 -> Create
/experiences/:id        -> ExperienceDetail
/analysis-result        -> AiAnalysisResultPage
/mypage                 -> MyPage
```

특징은 아래와 같습니다.

- 중첩 라우트 구조는 아직 쓰지 않고 있음
- `createBrowserRouter` / loader / action 패턴은 아직 미도입
- 페이지 이동은 대부분 `useNavigate()`로 처리
- 결과 페이지는 path param이 아니라 query string으로 진입
  - 예: `/analysis-result?experienceId=12`

결과 페이지 작업 시 가장 먼저 보면 되는 파일은 아래입니다.

- `fe/src/pages/AiAnalysisResultPage.tsx`
- `fe/src/components/ai-analysis/AiAnalysisResult.tsx`

## 6. 공통 레이아웃 방식

공통 화면은 `src/components/layout/Layout.tsx`를 감싸서 사용합니다.

`Layout`이 담당하는 것:

- 모바일 기준 최대 폭 고정(`max-w-[375px]`)
- 상단 헤더 노출 여부
- 하단 탭바 노출 여부
- 뒤로가기 / 메뉴 / 우측 아이콘 처리
- 본문 상단/하단 여백 확보

대표 사용 예시는 `Home.tsx`, `Create.tsx`입니다.

반면 결과 페이지 `AiAnalysisResultPage.tsx`는 현재 `Layout`을 쓰지 않고,  
상단 헤더와 하단 네비게이션을 페이지 안에서 직접 구성하고 있습니다.

즉, 결과 페이지는 지금 기준으로는 “공통 레이아웃 일부 재사용 + 상세 화면 커스텀 UI”에 가깝습니다.

## 7. 컴포넌트 라이브러리 사용 방식

현재 상태를 정리하면 아래와 같습니다.

### 외부 컴포넌트 라이브러리

- 별도 외부 UI 컴포넌트 라이브러리는 사용하지 않음
- 아이콘 라이브러리로는 `lucide-react`가 의존성에 있으나, 실제 화면은 SVG asset 또는 inline SVG를 직접 쓰는 비중이 큼

### 내부 컴포넌트 라이브러리

사실상 `src/components`가 내부 컴포넌트 라이브러리 역할을 합니다.

주요 재사용 기준:

- `common/`: 프로젝트 전반에서 재사용 가능한 가장 작은 UI 단위
- `layout/`: 페이지 뼈대
- 기능별 폴더(`auth`, `experience-write`, `ai-analysis`)는 도메인 전용 컴포넌트 묶음

예시:

- `common/SearchBar.tsx`: 홈 검색창
- `common/Card.tsx`: 카드형 리스트 UI
- `layout/Layout.tsx`: 공통 프레임
- `experience-write/*`: 작성 단계별 조립형 컴포넌트
- `ai-analysis/AiAnalysisResult.tsx`: 결과 페이지 본문 조립

권장 사용 방식은 아래처럼 보면 됩니다.

1. 여러 페이지에서 재사용되면 `common/`
2. 헤더/탭바/프레임이면 `layout/`
3. 특정 기능에서만 쓰면 기능별 폴더 하위

## 8. 스타일링 방식

스타일은 Tailwind utility class 중심입니다.

- 전역 스타일: `src/styles/globals.css`
- 폰트: Pretendard CDN import
- 페이지/컴포넌트 내부에서 Tailwind class를 직접 작성

현재 특징:

- 모바일 시안 기준 고정 폭 레이아웃이 많음
- px 단위 수치가 비교적 직접적으로 들어가 있음
- 별도 design token 파일이나 theme 확장은 아직 거의 없음

즉, 지금은 “디자인 시스템 기반”보다는 “컴포넌트별 Tailwind 직접 스타일링”에 가깝습니다.

## 9. 데이터 연동 방식

API 호출은 `src/lib/api.ts`에 모아두고 있습니다.

패턴:

- `API_BASE_URL` 환경변수 사용
- 공통 `request<T>()` 함수로 fetch 래핑
- 응답 envelope(`success`, `message`, `data`) 기준 처리
- 에러는 `ApiError`로 변환

페이지/컴포넌트에서는 보통 아래 방식으로 사용합니다.

1. `lib/api.ts`에서 함수 import
2. `useEffect`에서 비동기 호출
3. `loading`, `error`, `data`를 컴포넌트 state로 관리

예시:

- `Home.tsx` -> `getExperiences()`, `getMe()`
- `Create.tsx` -> `getCategories()`, `createExperience()`
- `AiAnalysisResult.tsx` -> `getExperience()`, `getReport()`, 필요 시 `createAnalysis()`

## 10. 결과 페이지 기준으로 보면

결과 페이지 작업자가 바로 알아야 할 포인트는 아래입니다.

### 진입

- URL: `/analysis-result?experienceId={id}`

### 화면 파일

- 페이지 래퍼: `fe/src/pages/AiAnalysisResultPage.tsx`
- 실제 본문: `fe/src/components/ai-analysis/AiAnalysisResult.tsx`

### 현재 데이터 흐름

1. query string에서 `experienceId` 추출
2. `getExperience(experienceId)` 호출
3. `getReport(experienceId)` 호출
4. report 상태가 `NOT_READY`이고 토큰이 있으면 `createAnalysis()` 재시도
5. 결과 데이터를 section 단위로 렌더링

### 결과 페이지 전용 컴포넌트 폴더

`src/components/ai-analysis/`

- `AiAnalysisResult.tsx`
- `ActionCard.tsx`
- `PatternBar.tsx`
- `SimilarCaseCard.tsx`

즉, 결과 페이지는 별도 기능 폴더로 분리되어 있어서, 이 폴더 안에서 확장하는 방식이 가장 자연스럽습니다.

## 11. 작업 시 추천 규칙

결과 페이지 포함 이후 작업은 아래 기준으로 맞추면 됩니다.

1. 페이지 라우트는 `src/pages`에 둠
2. 페이지 내부 섹션 분리는 `src/components/{기능명}` 아래로 이동
3. 공통화 가능한 버튼/카드/입력은 `src/components/common`으로 승격
4. API 함수 추가는 `src/lib/api.ts`에 모음
5. 인증 토큰 참조는 `src/lib/session.ts` 사용
6. 페이지 이동은 `useNavigate`, URL 파라미터는 `useSearchParams` 또는 `:id` 사용

## 12. 한 줄 요약

현재 프론트는 `pages + 기능별 components + lib/api + Tailwind 직접 스타일링` 구조입니다.  
외부 UI 라이브러리 없이 내부 컴포넌트를 쌓아가는 방식이고, 라우팅은 `BrowserRouter` 기반 단순 선언형 구조입니다.
