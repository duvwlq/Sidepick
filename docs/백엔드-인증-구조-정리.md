# 백엔드 인증 구조 정리

## 목표

- 운영 환경에서 카카오 로그인만 안정적으로 제공한다.
- 이메일 로그인/회원가입은 설정으로 비활성화할 수 있게 유지한다.
- 사용자 식별은 JWT와 `/api/users/me` 중심으로 고정한다.
- 인증 책임을 서비스별로 분리해 유지보수를 쉽게 만든다.

## 현재 구조

### 인증 제공자 설정

운영/개발 환경에 따라 아래 설정으로 인증 수단을 제어한다.

```env
APP_AUTH_LOCAL_ENABLED='false'
APP_AUTH_KAKAO_ENABLED='true'
APP_AUTH_GOOGLE_ENABLED='false'
```

### 서비스 구성

- `AuthService`
  - 인증 진입점 역할만 담당하는 파사드
- `LocalAuthService`
  - 이메일 회원가입
  - 이메일/비밀번호 로그인
- `OAuthAuthService`
  - 카카오 로그인
  - 구글 로그인
  - 소셜 계정 연결 처리
- `EmailVerificationService`
  - 인증 코드 발급
  - 코드 검증
  - 회원가입 전 이메일 검증 상태 확인
- `AuthTokenService`
  - Access/Refresh Token 발급
  - `AuthPayload` 조립
- `EmailVerificationMailService`
  - SMTP/SES 기반 인증 메일 발송

## 사용자 식별 방식

- 프론트에서 `userId`를 직접 전달하지 않는다.
- 로그인 후에는 JWT를 사용한다.
- 사용자 정보는 `/api/users/me`를 통해 조회한다.
- 작성/수정/삭제 권한은 서버에서 현재 인증 사용자 기준으로 판정한다.

## 소셜 계정 연결 정책

- 카카오 로그인 성공 시 `social_accounts` 기준으로 기존 연결을 우선 조회한다.
- 연결된 계정이 없으면 `users`와 `social_accounts`를 함께 생성한다.
- 소셜 계정 사용자는 `auth_provider = KAKAO`로 관리한다.

## 운영 기준

- 운영 로그인 기본 수단: 카카오 로그인
- 이메일 로그인/회원가입: 준비 중 또는 설정으로 비활성
- 구글 로그인: 보류

## 점검 포인트

- 카카오 Redirect URI가 운영 도메인과 일치하는지 확인
- `APP_AUTH_*_ENABLED` 값이 운영 의도와 맞는지 확인
- `/api/users/me` 응답이 프론트 세션 구조와 일치하는지 확인
- 인증 실패 시 예외 메시지가 사용자에게 설명 가능한 수준인지 확인
