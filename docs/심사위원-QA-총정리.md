# SidePick 심사위원 Q&A 총정리

이 문서는 SidePick 프로젝트의 예상 심사 질문을 `백엔드`, `프론트엔드`, `클라우드/운영` 관점으로 나눠 정리한 발표 직전용 문서입니다.

핵심 원칙:

- 이론 설명보다 `왜 그렇게 선택했는지`를 답한다.
- 과장된 아키텍처보다 `MVP 단계에서의 현실적인 선택`을 설명한다.
- 답변은 `현재 판단`, `장점`, `한계`, `다음 개선 포인트` 순서로 말한다.

---

## 1. 백엔드 예상 질문

### 1-1. 구조 / 아키텍처

#### Q. 왜 AI 서버를 Spring Boot 안에 넣지 않고 FastAPI로 분리했나요?

- 답변 방향:
  AI 분석 영역은 SBERT, FAISS 같은 Python 생태계 활용성이 중요했습니다. 그래서 Spring Boot 안에 넣기보다 FastAPI로 분리해서 모델 실험과 서비스 API를 나눴습니다. 대신 프론트가 직접 AI를 호출하지 않고 Spring Boot를 통해 통제해서 응답 형식과 장애 처리를 일관되게 관리했습니다.
- 핵심 키워드:
  `Python 생태계`, `역할 분리`, `응답 통제`, `장애 격리`
- 꼬리 질문:
  운영 복잡도 증가하지 않나요?
- 대응:
  맞습니다. 대신 AI 변경이 메인 API 배포에 영향을 주지 않는 장점이 더 크다고 판단했습니다. 현재는 Docker Compose 기반 단일 EC2라 운영 복잡도도 과하지 않게 유지하고 있습니다.

#### Q. 왜 프론트가 AI 서버를 직접 호출하지 않게 했나요?

- 답변 방향:
  AI 응답 형식, 장애 처리, 보안 통제를 한 곳에서 관리하기 위해서입니다. 백엔드가 중간 조정자 역할을 하도록 설계했습니다.
- 핵심 키워드:
  `백엔드 조정자`, `계약 통제`, `보안`, `에러 일관성`

#### Q. 왜 MSA로 가지 않고 현재 구조로 갔나요?

- 답변 방향:
  현재 문제 크기 대비 운영 복잡도가 너무 커진다고 판단했습니다. 지금은 프론트, 백엔드, AI를 논리적으로 분리하는 수준이면 충분했고, 실제 트래픽과 운영 요구가 커질 때 더 세분화하는 게 맞다고 봤습니다.
- 핵심 키워드:
  `문제 크기 대비`, `과설계 방지`, `운영 복잡도`

### 1-2. API 계약 / 상태 설계

#### Q. 왜 `NOT_READY`를 에러가 아니라 상태로 처리했나요?

- 답변 방향:
  AI 결과 생성 지연은 실패가 아니라 정상 흐름이라고 봤습니다. 그래서 5xx 에러 대신 `READY / NOT_READY` 상태를 분리했고, 프론트도 실패 토스트 대신 준비중 UI를 보여주도록 설계했습니다.
- 핵심 키워드:
  `상태와 장애 분리`, `정상 지연`, `UX 안정성`, `계약 설계`
- 꼬리 질문:
  그냥 404나 500으로 주면 안 되나요?
- 대응:
  그렇게 하면 프론트가 실제 장애와 단순 대기 상태를 구분하기 어렵습니다. 그래서 준비중은 상태로, 실제 실패는 에러코드로 나눴습니다.

#### Q. 왜 공통 응답 envelope를 만들었나요?

- 답변 방향:
  프론트와 백엔드가 분리된 구조라 성공/실패 응답 형식을 통일할 필요가 있었습니다. 그래서 `success`, `message`, `errorCode`, `data` 구조를 고정해서 파싱 안정성을 높였습니다.
- 핵심 키워드:
  `응답 일관성`, `협업 안정성`, `파싱 안정성`

#### Q. 왜 공통 `errorCode` 구조를 만들었나요?

- 답변 방향:
  문자열 메시지 기반 분기는 프론트가 쉽게 깨졌습니다. 그래서 `errorCode`를 기준으로 사용자 메시지와 내부 로그를 분리해서, 계약 안정성과 운영 추적성을 같이 확보하려고 했습니다.
- 핵심 키워드:
  `계약 안정성`, `메시지 분리`, `로그 분리`
- 꼬리 질문:
  HTTP status만으로 충분하지 않나요?
- 대응:
  HTTP status는 범위가 넓어서 프론트가 세부적으로 대응하기 어렵습니다. 예를 들어 validation error와 AI timeout은 둘 다 실패지만 대응 방식이 다릅니다.

#### Q. 가장 어려웠던 실제 문제는 무엇이었나요?

- 답변 방향:
  FE/BE API 계약 충돌이 가장 어려웠습니다. 특히 AI 분석이 아직 생성되지 않은 상태를 에러로 볼지 상태로 볼지가 많이 충돌했습니다. 이후 공통 응답 구조와 `errorCode` 기반 계약으로 정리하면서 안정화했습니다.
- 핵심 키워드:
  `협업 문제`, `API 계약`, `상태 정의`, `공통 구조`

### 1-3. 인증 / 보안

#### Q. 왜 JWT 기반 인증을 선택했나요?

- 답변 방향:
  프론트와 API 서버가 분리된 구조에서 stateless 인증이 운영상 단순했습니다. Spring Security와도 잘 맞아서 MVP 단계에서 구현과 유지보수 효율이 좋았습니다.
- 핵심 키워드:
  `stateless`, `분리 구조`, `운영 단순성`

#### Q. 왜 공개 GET 엔드포인트를 많이 열어뒀나요?

- 답변 방향:
  SidePick은 사례 탐색 성격이 강해서 읽기 중심 콘텐츠는 공개 접근성이 중요했습니다. 대신 쓰기, 마이페이지, 사용자 수정 같은 부분은 인증을 걸어 분리했습니다.
- 핵심 키워드:
  `탐색 서비스`, `읽기 공개`, `쓰기 보호`
- 꼬리 질문:
  비공개 데이터가 생기면요?
- 대응:
  현재는 공개 사례 중심이고, private 요구가 강해지면 리포트와 상세 접근 정책까지 더 강화할 계획입니다.

#### Q. 보안적으로 가장 신경 쓴 부분은 무엇인가요?

- 답변 방향:
  클라이언트 입력을 그대로 신뢰하지 않고 서버에서 다시 검증하는 점입니다. 인증 정보 보호, 권한 체크, 민감 정보 노출 방지도 기본 원칙으로 두고 있습니다.
- 핵심 키워드:
  `서버 재검증`, `권한 체크`, `민감정보 보호`

### 1-4. AI 서버 연동 / 장애 대응

#### Q. AI 서버가 죽으면 서비스 전체도 죽나요?

- 답변 방향:
  아닙니다. 경험 저장과 AI 분석을 분리해서 처리했기 때문에, AI 서버 장애가 나도 경험 등록 자체는 유지되도록 설계했습니다. 분석 결과만 비어 있거나 `NOT_READY` 상태로 처리됩니다.
- 핵심 키워드:
  `graceful fallback`, `경험 저장 우선`, `장애 격리`

#### Q. 왜 Redis / WebSocket / Queue 안 썼나요?

- 답변 방향:
  현재는 MVP 단계라 실제 병목보다 기능 검증 속도가 더 중요했습니다. 분석 상태는 polling으로 충분했고, Redis나 Queue는 동시 사용자 수와 분석 대기시간이 커질 때 도입하는 게 더 현실적이라고 판단했습니다.
- 핵심 키워드:
  `MVP`, `과설계 방지`, `운영 복잡도 절감`
- 절대 하면 안 되는 답변:
  구현을 못해서요.

#### Q. 현재 구조에서 가장 큰 병목은 무엇인가요?

- 답변 방향:
  현재는 AI 동기 호출과 일부 메모리 후처리가 가장 큰 병목 후보입니다. 특히 분석 생성이 길어질 경우 Queue 기반 비동기화가 다음 개선 포인트입니다.
- 핵심 키워드:
  `AI 동기 호출`, `메모리 후처리`, `비동기화`

#### Q. 장애가 나면 어디서부터 확인하나요?

- 답변 방향:
  먼저 Nginx에서 외부 진입이 정상인지 보고, 그다음 Spring Boot 로그와 AI 서버 로그를 확인합니다. 요청 단위 추적은 `traceId` 기준으로 보고, DB 연결 문제인지 AI upstream 문제인지 분리해서 확인합니다.
- 핵심 키워드:
  `Nginx`, `application log`, `traceId`, `DB/AI 분리 확인`

### 1-5. DB / JPA / 성능

#### Q. 왜 `open-in-view: false`로 뒀나요?

- 답변 방향:
  컨트롤러 바깥 lazy loading에 의존하지 않고, 필요한 조회를 service/repository 단계에서 명시적으로 처리하려고 했습니다. 구조를 더 예측 가능하게 가져가기 위한 선택입니다.
- 핵심 키워드:
  `명시적 fetch`, `레이어 책임`, `예측 가능성`

#### Q. 왜 일부 조회는 메모리 후처리가 섞여 있나요?

- 답변 방향:
  MVP 단계에서는 데이터 규모가 크지 않아 구현 단순성을 우선했습니다. 다만 사용량이 늘어나면 이 부분은 DB 쿼리 최적화나 캐시, 비동기 처리로 옮겨야 하는 병목 후보로 보고 있습니다.
- 핵심 키워드:
  `MVP 단순화`, `데이터 규모`, `명확한 한계 인식`

#### Q. 왜 `ddl-auto: validate`로 운영하나요?

- 답변 방향:
  운영 DB 스키마를 애플리케이션이 임의로 변경하지 않게 하고, 스키마 변경은 migration 기준으로 관리하려고 했습니다. 운영에서는 자동 생성보다 검증 모드가 더 안전하다고 판단했습니다.
- 핵심 키워드:
  `운영 안정성`, `스키마 통제`, `migration 중심`

## 2. 프론트엔드 예상 질문

### 2-1. React 구조 / 상태 관리

#### Q. 왜 전역 상태 라이브러리를 안 썼나요?

- 답변 방향:
  현재 상태 복잡도가 Redux나 Zustand까지 필요한 수준은 아니라고 판단했습니다. 인증 정도만 Context로 처리하고, 나머지는 페이지 로컬 상태로 유지하는 쪽이 더 단순하고 관리하기 좋았습니다.
- 핵심 키워드:
  `상태 복잡도`, `과설계 방지`, `Context 최소 사용`, `로컬 상태`

#### Q. 왜 매핑 레이어를 따로 뒀나요?

- 답변 방향:
  백엔드 DTO를 그대로 UI에 연결하면 계약이 조금만 바뀌어도 화면 전체 영향이 커집니다. 그래서 프론트에서 화면 모델로 한 번 변환하는 레이어를 두었습니다.
- 핵심 키워드:
  `UI 보호`, `계약 변화 흡수`, `결합도 감소`

#### Q. 왜 페이지별 fetch 구조로 갔나요?

- 답변 방향:
  현재 서비스 규모에서는 화면 책임과 데이터 흐름이 비교적 명확해서, 각 페이지가 필요한 데이터를 직접 가져오는 구조가 더 단순했습니다. 불필요한 전역 복잡도를 만들지 않으려는 판단이었습니다.
- 핵심 키워드:
  `단순한 데이터 흐름`, `화면 책임 분리`

### 2-2. API 연동 / 에러 UX

#### Q. 왜 `ApiError` 같은 별도 에러 구조를 만들었나요?

- 답변 방향:
  네트워크 오류, 서버 오류, 비즈니스 오류를 프론트가 다르게 처리해야 했기 때문입니다. 그래서 status, code, rawMessage를 같이 들고 가는 구조로 만들어 UX와 디버깅을 분리했습니다.
- 핵심 키워드:
  `에러 분류`, `UX 분기`, `디버깅 편의성`

#### Q. 왜 `NOT_READY`에서는 실패 화면이 아니라 준비중 화면을 보여주나요?

- 답변 방향:
  그 상태는 실패가 아니라 분석이 아직 끝나지 않은 정상 흐름이기 때문입니다. 사용자가 서비스가 깨졌다고 느끼지 않도록 상태를 분리했습니다.
- 핵심 키워드:
  `상태와 장애 분리`, `사용자 혼란 방지`

#### Q. 왜 `errorCode` 기반으로 프론트 메시지를 처리했나요?

- 답변 방향:
  백엔드 메시지 문자열이 바뀌어도 프론트 분기가 깨지지 않게 하려는 목적이었습니다. 사용자에게 보여줄 문구와 서버 내부 원인을 분리하려고 했습니다.
- 핵심 키워드:
  `메시지와 계약 분리`, `프론트 안정성`

#### Q. 왜 polling으로 분석 완료를 확인했나요?

- 답변 방향:
  현재는 분석 상태 확인 빈도와 사용량을 고려하면 polling이 가장 단순하고 안정적이었습니다. WebSocket이나 SSE는 이후 실시간 요구가 커질 때 도입하는 게 맞다고 봤습니다.
- 핵심 키워드:
  `단순성`, `안정성`, `현재 요구사항 적합성`

---

### 2-3. 컴포넌트 / UX / 반응형

#### Q. 왜 분석 결과 화면을 별도 컴포넌트로 분리했나요?

- 답변 방향:
  상세 라우팅 책임과 결과 렌더링 책임을 분리하기 위해서입니다. 화면 구조가 커질수록 페이지 컴포넌트가 비대해지는 걸 막는 목적도 있었습니다.
- 핵심 키워드:
  `책임 분리`, `유지보수성`, `컴포넌트 경량화`

#### Q. 왜 모바일 중심 레이아웃으로 잡았나요?

- 답변 방향:
  부업 경험 기록과 탐색은 모바일에서 소비될 가능성이 높다고 봤습니다. 그래서 작은 화면에서 핵심 흐름이 먼저 자연스럽게 보이도록 설계했습니다.
- 핵심 키워드:
  `모바일 우선`, `사용 시나리오 중심`

#### Q. 사용자 경험 측면에서 가장 신경 쓴 부분은 무엇인가요?

- 답변 방향:
  사용자가 지금 어떤 상태에 있는지 명확하게 보여주는 점입니다. 특히 로딩, 준비중, 실패 상태를 섞지 않고 분리해서 혼란이 없도록 하는 데 집중했습니다.
- 핵심 키워드:
  `상태 가시성`, `혼란 방지`, `명확한 흐름`

#### Q. Tailwind를 선택한 이유는 무엇인가요?

- 답변 방향:
  MVP 단계에서 빠르게 화면을 구현하고 일관된 스타일 규칙을 유지하기에 효율적이었습니다. 별도의 CSS 구조를 크게 만들기보다 컴포넌트 단위로 빠르게 반복 구현하는 데 적합했습니다.
- 핵심 키워드:
  `빠른 구현`, `스타일 일관성`, `MVP 적합성`

#### Q. 프론트에서 가장 어려웠던 점은 무엇이었나요?

- 답변 방향:
  백엔드 응답 상태에 따라 화면이 달라지는 부분이 가장 까다로웠습니다. 그래서 정상 응답만 가정하지 않고 로딩, 준비중, 실패 상태까지 분리해서 처리했습니다.
- 핵심 키워드:
  `상태 분기`, `방어적 UI`, `API 의존 화면`

## 3. 클라우드 / 운영 예상 질문

### 3-1. 배포 구조

#### Q. 왜 프론트는 Amplify, 백엔드와 AI는 EC2로 분리했나요?

- 답변 방향:
  프론트는 정적 자산이라 Amplify가 배포와 캐시 관리에 효율적이었고, 백엔드와 AI 서버는 프로세스 제어와 네트워크 구성이 필요해서 EC2에서 운영했습니다. 각 레이어 성격이 달라서 분리하는 게 더 단순하고 관리하기 좋았습니다.
- 핵심 키워드:
  `정적 호스팅`, `서버 프로세스 제어`, `역할 분리`

#### Q. 왜 EC2 한 대에 Docker Compose로 운영했나요?

- 답변 방향:
  현재는 MVP 단계라 트래픽 규모보다 빠른 배포와 운영 단순성이 더 중요했습니다. ECS나 Kubernetes보다 단일 EC2 + Docker Compose가 현재 팀 규모와 운영 난이도에 더 맞는 선택이라고 판단했습니다.
- 핵심 키워드:
  `MVP`, `운영 단순성`, `배포 속도`, `과설계 방지`
- 꼬리 질문:
  단일 서버면 위험하지 않나요?
- 대응:
  맞습니다. 다만 현재 단계에서는 복잡한 오케스트레이션보다 운영 가능한 구조를 우선했고, 장애 범위가 커질 정도로 사용량이 늘어나면 점진적으로 분리할 계획입니다.

#### Q. 왜 Nginx Reverse Proxy를 넣었나요?

- 답변 방향:
  외부 진입점을 하나로 통합하고, HTTPS 처리와 경로 기반 라우팅을 하려고 넣었습니다. 실제로 `/api`는 Spring Boot로, `/ai`는 FastAPI로 보내도록 분기해서 운영하고 있습니다.
- 핵심 키워드:
  `HTTPS 종료`, `단일 진입점`, `경로 기반 라우팅`

#### Q. 왜 `/api`와 `/ai`를 나눴나요?

- 답변 방향:
  서비스 API와 AI 서버를 논리적으로 분리하기 위해서입니다. 다만 프론트는 AI를 직접 호출하지 않고, 실제 서비스 흐름은 Spring Boot가 통제해서 응답 형식과 장애 처리를 일관되게 관리했습니다.
- 핵심 키워드:
  `논리적 분리`, `응답 통제`, `장애 격리`

#### Q. 왜 RDS를 따로 썼나요?

- 답변 방향:
  앱 컨테이너와 DB 수명을 분리하기 위해서입니다. 서버 재배포나 컨테이너 재시작이 있어도 데이터 저장소는 안정적으로 유지하는 게 더 중요하다고 봤습니다.
- 핵심 키워드:
  `데이터 영속성`, `앱/DB 분리`, `운영 안정성`

---

### 3-2. 운영 / 보안 / 장애 대응

#### Q. 왜 백엔드와 AI 서버 포트를 직접 외부에 노출하지 않았나요?

- 답변 방향:
  외부에는 Nginx만 노출하고, 백엔드와 AI 서버는 로컬 바인딩으로 두어서 외부 접근 경로를 줄였습니다. 운영 서버에서 진입점을 최소화하는 게 더 안전하다고 판단했습니다.
- 핵심 키워드:
  `공격면 축소`, `진입점 최소화`, `리버스 프록시 통제`

#### Q. 운영 중 장애가 나면 어디부터 확인하나요?

- 답변 방향:
  먼저 Nginx 레벨에서 외부 진입이 정상인지 보고, 그다음 Spring Boot 로그와 AI 서버 로그를 확인합니다. 요청 단위 추적은 `traceId` 기준으로 보고, DB 연결 문제인지 AI upstream 문제인지 분리해서 확인합니다.
- 핵심 키워드:
  `Nginx`, `application log`, `traceId`, `DB/AI 분리`

#### Q. `traceId`를 왜 넣었나요?

- 답변 방향:
  운영 중 에러가 나면 어떤 요청에서 문제가 났는지 빠르게 추적해야 하기 때문입니다. 사용자 문의나 장애 로그를 요청 단위로 묶어 확인할 수 있게 하려고 넣었습니다.
- 핵심 키워드:
  `요청 추적`, `운영 디버깅`, `로그 연결`

#### Q. AI 서버가 죽으면 서비스는 어떻게 되나요?

- 답변 방향:
  경험 저장은 유지하고 분석만 fallback 처리합니다. 즉 AI 장애를 서비스 전체 장애와 동일하게 보지 않도록 설계했습니다.
- 핵심 키워드:
  `graceful fallback`, `경험 저장 우선`, `AI 장애 격리`

#### Q. 현재 운영 구조의 가장 큰 리스크는 무엇인가요?

- 답변 방향:
  단일 EC2 기반이라 인프라 장애 시 영향 범위가 넓다는 점입니다. 지금은 단순성을 우선했지만, 서비스 규모가 커지면 점진적인 이중화가 필요합니다.
- 핵심 키워드:
  `단일 장애 지점`, `MVP 단순성`, `향후 이중화`

---

### 3-3. 기술 선택 이유

#### Q. 왜 ECS나 Kubernetes를 쓰지 않았나요?

- 답변 방향:
  현재 서비스 규모와 팀 운영 역량 기준에서는 오히려 복잡도가 더 커진다고 판단했습니다. 지금은 단일 EC2와 Compose로도 충분히 운영 가능했고, 구조를 이해하고 직접 제어할 수 있는 쪽이 더 중요했습니다.
- 핵심 키워드:
  `문제 크기 대비`, `운영 복잡도`, `직접 제어 가능성`

#### Q. 왜 Docker로 운영했나요?

- 답변 방향:
  백엔드와 AI 서버 실행 환경을 고정하고, 로컬과 운영 환경 차이를 줄이기 위해서입니다. 특히 팀 협업에서 환경 차이로 인한 문제를 줄이는 데 도움이 됐습니다.
- 핵심 키워드:
  `환경 일관성`, `재현 가능성`, `배포 단순화`

#### Q. 배포할 때 가장 신경 쓴 점은 무엇인가요?

- 답변 방향:
  환경변수 분리와 서비스 간 연결 안정성입니다. 특히 DB, JWT secret, OAuth, AI 서버 URL 같은 값들이 운영 환경에서 정확히 분리되도록 관리하는 데 신경 썼습니다.
- 핵심 키워드:
  `환경변수`, `비밀값 분리`, `서비스 연결 안정성`
