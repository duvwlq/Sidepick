## 1. case_id 인용 형식 검증

### 정규식 (혼합 형식 + 정책 문서 출처 + 안내 라벨) — v1.2

```python
import re

# 7개 부업 카테고리 enum (전체 시스템 통일 — 카테고리 화이트리스트와 동일)
ALLOWED_CATEGORIES = [
    "온라인 판매·이커머스",
    "콘텐츠·SNS",
    "디지털·지식판매",
    "플랫폼 노동",
    "재능·프리랜서",
    "투자·재테크",
    "오프라인 부업"
]

# 정책 문서 출처 enum (실제 문서 존재)
ALLOWED_POLICY_DOCS = [
    "사이드픽 서비스 정책",   # → docs/사이드픽-서비스-정책.md
    "사이드픽 안전 정책",     # → docs/사이드픽-안전-정책.md
]

# 상황 안내 라벨 (실제 데이터·문서 없음 / "[안내: ...]" 형식)
SPECIAL_LABELS = {
    "[안내: 사례 0건]",           # Tool 결과 0건
    "[안내: 추가 정보 필요]",     # 모호 질문 / 추가 정보 요청
    "[안내: 가이드 페이지 안내]", # 횡단 주제(세금·법률·멘탈 등) 질문 시 가이드 페이지로 유도 (v1.3)
}

# 정규식 변환 (특수문자 escape)
category_pattern = "|".join(re.escape(c) for c in ALLOWED_CATEGORIES)
policy_pattern = "|".join(re.escape(p) for p in ALLOWED_POLICY_DOCS)

# 단일 아이템 패턴 (case_id / 업종 통계 / 정책 문서)
item_pattern = rf"(case_\d+|업종 통계 — ({category_pattern})|{policy_pattern})"

# 최종 정규식: 혼합 형식 지원
CITATION_PATTERN = rf"\[출처:\s*{item_pattern}(,\s*{item_pattern})*\s*\]"


def validate_citation(response: str) -> bool:
    """LLM 응답 인용 검증 (출처 + 안내 라벨)

    검증 흐름:
    1. 안내 라벨 우선 검증 ([안내: ...] 형식 — 사례 0건 / 모호 질문)
    2. 출처 정규식 검증 (case_id / 업종 통계 / 정책 문서 / 혼합 형식)
    """
    # 1차: 안내 라벨 검증
    if any(label in response for label in SPECIAL_LABELS):
        return True
    # 2차: 출처 정규식 검증
    return bool(re.search(CITATION_PATTERN, response))
```

### 허용 형식

**출처 (실제 데이터·문서 인용 — `[출처: ...]` 형식)**:
- `[출처: case_042]` — 사례 1개
- `[출처: case_042, case_077, case_108]` — 사례 여러 개
- `[출처: 업종 통계 — 콘텐츠·SNS]` — 업종별 통계 (영문 알파벳 포함 OK)
- `[출처: 업종 통계 — 온라인 판매·이커머스]` — 한글+공백+가운뎃점 카테고리
- `[출처: 사이드픽 서비스 정책]` — 7개 카테고리 외 질문 (정책 문서 인용)
- `[출처: 사이드픽 안전 정책]` — 위험 차단 키워드 감지 (안전 정책 문서 인용)
- `[출처: case_042, case_077, 업종 통계 — 콘텐츠·SNS]` — **혼합 형식 ✨ (v1.1)**

**안내 라벨 (실제 데이터·문서 없음 — `[안내: ...]` 형식)**:
- `[안내: 사례 0건]` — Tool 결과 0건일 때
- `[안내: 추가 정보 필요]` — 모호 질문 되묻기 응답 시
- `[안내: 가이드 페이지 안내]` — 횡단 주제(세금·법률·멘탈관리 등) 질문 시 가이드 페이지로 유도 (v1.3)

### 거부 형식 (환각 의심)
- `[출처: 업종 통계 — 주식 단타]` — 7개 카테고리 외 ❌
- `[출처: 업종 통계 — 코인]` — enum에 없는 카테고리 ❌
- `[출처: case_abc]` — 숫자 ID 아님 ❌
- `[출처: 통계 자료]` — "업종 통계 — " prefix 없음 ❌
- 인용 자체 누락 (특수 케이스 enum에도 없는 경우) ❌

### 검증 실패 시
1. 같은 prompt로 재생성 (max 1회)
2. 재생성도 실패 시 Plan B (단순 RAG fallback)

### enum 방식 채택 이유
- `[가-힣·\s]+` 같은 정규식 범위 표현 대신 7개 카테고리를 직접 enum으로 매칭 → 가독성 ↑
- 카테고리 화이트리스트 검증(2번)과 동일한 `ALLOWED_CATEGORIES` 변수 사용 → 일관성 ↑
- 카테고리 추가/변경 시 한 곳만 수정하면 됨

### v1.1 변경 사항 — 혼합 형식 + 특수 케이스 추가 이유
1차 리뷰에서 발견된 2가지 문제 해결:
1. **혼합 형식 미지원**: 통계 + 사례 종합 응답이 정상이지만 BE 검증에서 환각 오판
   → `item_pattern` 분리 + 반복 매칭(`(,\s*{item_pattern})*`)으로 해결
2. **case_id 인용 누락 문제**: 정보 없는 질문 / 카테고리 외 질문 답변에 case_id 없음
   → 특수 케이스 4종 인용 형식 도입

### v1.2 변경 사항 — "출처" vs "안내" 분리
2차 검토에서 발견된 의미 명확화 필요:
1. **"출처"라는 표현이 헷갈림**: 실제 데이터 없는데 `[출처: 사이드픽 서비스 정책]`라고 쓰면 "실제 문서 있어?"라고 오해
   → 해결: 실제 정책 문서 2종 작성 (`docs/사이드픽-서비스-정책.md`, `docs/사이드픽-안전-정책.md`) → 진짜 출처로 사용
2. **데이터·문서 없는 상황은 "안내" 라벨로 분리**:
   - `[안내: 사례 0건]` (Tool 결과 0건)
   - `[안내: 추가 정보 필요]` (모호 질문 되묻기)
3. **명확화 효과**:
   - "출처" = 실제 데이터 / 정책 문서 존재
   - "안내" = 응답 상황 (데이터·문서 없음)
   - 사용자·BE·LLM 모두 의미 명확히 이해

## 3. 수치 검증

### 룰
- 응답의 "X%" / "X명" / "X건" 같은 수치는 반드시 Tool 결과(`query_stats`, `search_cases`)에 존재해야 함
- Tool 결과에 없는 수치 발견 시 → 환각으로 판단 → 재생성 → Plan B

### 구현 예시
```python
def validate_numbers(response: str, tool_results: list) -> bool:
    # 응답에서 모든 수치 추출
    response_numbers = set(re.findall(r'\d+(?:\.\d+)?%?', response))

    # Tool 결과에서 모든 수치 추출
    tool_numbers = set()
    for result in tool_results:
        tool_numbers.update(extract_numbers_from_dict(result))

    # 응답 수치가 Tool 결과에 모두 있는지 확인
    return response_numbers.issubset(tool_numbers)
```

## 5. case_id 존재 검증

### 룰
- 인용된 `case_id`가 실제 DB에 존재하는지 확인
- 존재하지 않는 `case_id` 인용 시 → 환각 → 재생성 → Plan B

### 구현 예시
```python
def validate_case_ids_exist(response: str) -> bool:
    cited_ids = re.findall(r'case_(\d+)', response)
    if not cited_ids:
        return True  # 통계만 사용한 경우

    # DB에서 case_id 존재 확인
    existing_ids = db.query("SELECT case_id FROM cases WHERE case_id IN %s", cited_ids)
    return set(cited_ids) == set(existing_ids)
```

## 6. 응답 검증 통합 흐름

```
[LLM 응답 수신]
   ↓
[1] BANNED_WORDS 검증
   - 차단 시 → 재생성 (max 1회) → Plan B
   ↓
[2] 카테고리 화이트리스트 검증
   - 외부 카테고리 시 → 재생성 → Plan B
   ↓
[3] 수치 검증
   - Tool 결과에 없는 수치 시 → 재생성 → Plan B
   ↓
[4] case_id 인용 형식 검증
   - 형식 미충족 시 → 재생성 → Plan B
   ↓
[5] case_id 존재 검증
   - DB에 없는 ID 시 → 재생성 → Plan B
   ↓
[검증 통과 → 사용자에게 응답 전달]
```

### 재생성 정책
- 모든 검증 실패 시 같은 룰
- **재생성 횟수: max 1회**
- 재생성도 실패 시 → **Plan B 자동 전환** (단순 RAG fallback)
- 로그: `validation_failure: {reason}` 형식으로 기록

## 9. 4주차 50개 시나리오 테스트 계획
