## 1. 고도화 수행 계획 개요

### 📊 AI / 콘텐츠
- 실패패턴 그래프 ("나와 같은 실수를 한 사람 X%") — 기존 칩에서 변경
- 실패 시점 분포 시각화
- 업종별 통계 페이지 + 실패 요인 TOP3
- 내 분석 결과 히스토리
- 성공사례 추가 (원글 + AI 분석글 / 나와 다른 점 비교)
- 부업 시작 전 실패 조심 안내 (성공 요인 부족 감지 → 유사 실패사례 연결)
- 부업 가이드 페이지 (검색창 + 업종별 카테고리 + 가이드라인)

### 🤖 AI 에이전트
- **[에이전트 A] 글 작성 보조 에이전트** — 초안 분석 후 부족한 정보를 질문 카드로 수집, 보완된 정보로 더 정밀한 분석 실행
- **[에이전트 B] 리포트 자기검증 루프** — AI 분석 신뢰도 < 0.7 발동 / 재생성 1회 / 결과 캐싱 (환각 방지 핵심 안전장치)
- **[에이전트 C] 부업 상담 에이전트** — Tool 2개 (FAISS 통합 검색 + 통계 조회), LangChain ReAct 루프로 멀티스텝 실행 / **Sonnet 단일 모델** (성능 + 컨텍스트 일관성 우선) / Plan B: ReAct 실패 시 단순 RAG fallback (기존 FAQ 챗봇 격상)
- **[에이전트 D] 프로액티브 알림 에이전트 — ⏸ v2.1로 이동** (런칭 후 사용자 데이터 누적 후 진행)

> 📌 에이전트 D를 v2.1로 이동한 이유: 웹 서비스 특성상 인앱 알림은 유저가 재방문해야 보임 → "프로액티브" 효과 약함. 사용자 데이터 누적 후 트리거가 의미있어지는 시점에 도입하는 게 맞음.

- 유사사례 좌우 분할 (왼쪽 성공사례 / 오른쪽 실패사례)

- 브랜드 컬러 확정 + 전체 디자인 개편 (현재 모노톤 → 컬러 적용)

### 👥 역할 분배
- **팀장**: PM 전체 (기획·일정·산출물 관리·QA)

## 2. 에이전트 C 운영 안전장치 (v6.1 업데이트) 🔴

> **P0 — 반드시 챙겨야 할 것들**
> ReAct 패턴은 질문 1회당 LLM을 5~7번 호출 → 토큰 비용 폭발 위험
> 발표 직전 API 한도 초과 = 최악의 시나리오

| 항목 | 내용 | 비고 |
|---|---|---|
| **Tool 수 제한** | FAISS 검색 + 통계 조회 2개만 (성공사례는 FAISS에 통합) | type 메타데이터 필터링 |
| **토큰 한도** | 유저당 일일 한도 10,000 + 하이브리드 라우팅 | 단순=RAG / 복잡=ReAct |
| **루프 제한** | max_iterations = 7 (무한 루프 방지) | 50개 테스트로 최적값 확정 |
| **응답 시간** | 30초 + 스트리밍 응답 (Server-Sent Events) | UX 개선 |
| **모델 선택** | **Sonnet 단일 모델 확정** (성능 + 컨텍스트 일관성 우선) | 환각 위험은 자기검증으로 커버 |
| **캐싱** | DB 답변 캐시 (통계 7d / 사례 24h) + Prompt Caching 활용 | 비용 절감 |
| **Plan B** | 실패 시 5가지 조건 명확히 정의 | 단순 RAG fallback |
| **모니터링** | LangSmith 무료 티어 + 일일 토큰 사용량 대시보드 | 디버깅 + 비용 추적 |
| **Tool 실패 처리** | 재시도 1회 + Plan B 자동 전환 | 안정성 |
| **대화 방식** | 단일턴 + "페이지를 나가면 이전 대화를 기억하지 못합니다" 안내 | 토큰 관리 |
| **한국어 튜닝** | 시스템 프롬프트 (Section 분리) + Tool 설명 한국어 | 50개 시나리오 테스트 |
| **자동 차단** | 80% 자동 차단 / 100% Plan B만 동작 | API 한도 보호 |
| **시연 안정성** | 4~5개 시연 질문 사전 캐싱 | 발표 안정성 |
| **가드레일** | 입력 (BANNED_WORDS) + 출력 (LLM 응답 필터) + 카테고리 화이트리스트 | 3중 방어 |
| **입력 길이** | 최대 500자 (FE + BE 양쪽 검증) | 토큰 폭발 방지 |
| **동시성** | BE 요청 큐잉 (Spring BlockingQueue) + "잠시만 기다려주세요" UX | Rate Limit 대응 |
| **비용 cap** | 사용자별 일일 $0.50 + 서비스 전체 일일 $5 | 학생 프로젝트 안전 |
| **타임존** | KST 자정 리셋 + 사용자 노출 KST | 한국 사용자 |
| **모델 ID 분리** | 환경 변수 `CLAUDE_MODEL`로 관리 | deprecated 대응 |
| **환각 방지** | 시스템 프롬프트 환각 룰 + case_id 인용 강제 + 응답 검증 + 자기검증 루프 | Sonnet 단일 보완 ⭐ |

### Tool 호출 방식 — 최종 결정

**데이터 구조**: FAISS 통합 인덱스 = 실패사례 임베딩 + 성공사례 임베딩
(각 데이터에 type 메타데이터: "failure" or "success")

```
Tool 1: search_cases(query, type="failure" or "success", limit=3)
        → FAISS 통합 인덱스, type 메타데이터로 필터링
        → 성공사례 검색은 type="success"로 통합
Tool 2: query_stats(category, metric)
        → 업종별 통계 / 실패 요인 TOP3

총 2개 Tool
```

**+ 성공사례 데이터 구조 설계 시 실패와 비슷한 스키마로 맞추기**
- 공통 필드: 원글 / 업종 / 기간 / 투자금 / 키워드 / AI 분석 / 메타 grid
- type별 추가:
  - failure: 실패 패턴, 핵심 이슈 칩
  - success: 성공 요인, 나와의 차이점

### 토큰 한도 — 하이브리드 라우팅

**[단순 질문] = Plan B (단순 RAG) 자동 라우팅**
- 일일 한도: 무제한 (또는 매우 높게)
- 비용 매우 적음 (Tool 호출 없음, 짧은 응답)

**[복잡 질문] = ReAct (멀티스텝)**
- 일일 한도: 10,000 토큰 유지 (사용자 결정대로)
- ReAct 발동 자체를 줄여서 비용 관리

**라우팅 규칙**:
- 질문 길이 < 30자 → 단순 RAG (Plan B)
- 질문에 "비교", "통계", "유사", "성공사례" 키워드 포함 → ReAct
- 그 외 → 단순 RAG

→ 사용자 입장: 일상적 질문은 한도 차감 X / 진지한 상담만 한도 차감
→ 비용 관점: ReAct 호출 자체가 줄어들어 절약

**추가 안전장치**:
- 사용자별 일일 비용 cap: $0.50/일 (10,000 토큰 = 약 $0.18, 여유 마진)
- 서비스 전체 일일 비용 cap: $5/일 (학생 프로젝트 안전 한도)
- 한도 도달 시 ReAct 자동 차단 / Plan B만 동작

### 응답 시간 — 스트리밍 응답

**스트리밍 응답 (Server-Sent Events)** — 사용자가 체감하는 응답 시간 단축
- "도구를 선택하고 있어요..." (1초)
- "FAISS 검색 중..." (3초)
- "결과 분석 중..." (6초)
- 최종 응답 실시간 출력 (10초)
- → 사용자는 "30초 기다리는" 게 아니라 "계속 뭔가 일어나는" 경험

### Plan B 트리거 조건별 동작 (5가지)

| # | 조건 | 동작 | 사용자 안내 | 빈도 예상 |
|---|---|---|---|---|
| 1 | max_iterations 초과 (7회 도달) | 마지막 Tool 결과 + 단순 LLM 응답으로 답변 생성 | ❌ 안내 X (백엔드만 인지) | 중간 (10~20%) |
| 2 | Tool 호출 결과 0건 (FAISS 검색 결과 없음) | 기본 응답 템플릿 사용 (업종별 일반 가이드) | ✅ "비슷한 사례를 찾지 못했어요. 일반적인 가이드를 안내드릴게요." | 낮음 (5~10%) |
| 3 | LLM 응답 파싱 실패 (JSON 깨짐, 형식 오류) | 같은 prompt로 1회 재시도 → 실패 시 단순 RAG fallback | ❌ 안내 X (백엔드만 인지) | 매우 낮음 (1~3%) |
| 4 | 응답 타임아웃 (30초 초과) | ReAct 진행 즉시 중단 → 5초 내 단순 RAG로 답변 생성 | ✅ "응답 생성에 시간이 더 필요했어요. 간단히 안내드릴게요." | 낮음 (3~5%) |
| 5 | Tool 호출 자체 실패 (API 에러, 네트워크) | 동일 Tool 1회 재시도 (0.5초 대기 후) → 재시도도 실패 시 ReAct 중단 → 단순 LLM 응답 | ❌ 안내 X (백엔드만 인지) | 매우 낮음 (1~3%) |

**Plan B 발동 합계 예상**: 약 20~40% (정상 ReAct = 60~80%)
→ 이 비율이 너무 높으면 ReAct 자체 품질 문제. 4주차 50개 시나리오 테스트에서 측정.

### 환각(Hallucination) 방지 — Sonnet 단일 보완 ⭐ 신규

> **Sonnet 단일 모델 선택의 trade-off**: 성능·컨텍스트 일관성 ↑ but 환각 위험 ↑
> → 이미 결정한 안전장치들로 커버 가능

**6가지 환각 방지 메커니즘**:

1. **에이전트 B 자기검증 루프** (핵심)
   - 신뢰도 < 0.7 발동 → 재생성 1회 → 결과 캐싱
   - 환각 잡아내는 핵심 안전장치

2. **시스템 프롬프트에 환각 방지 룰 명시**
   ```
   - Tool 결과에 명시된 정보만 사용하라
   - 근거 없는 통계나 수치를 만들지 마라
   - 정보가 부족하면 "비슷한 사례를 찾지 못했어요"라고 답하라
   - 모든 답변은 case_id 인용으로 끝나야 한다
   ```

3. **case_id 인용 강제 + 응답 검증 로직**
   - LLM 응답에 case_id 인용 여부 검증
   - 인용 없으면 환각으로 판단 → 재생성 (max 1회)
   - 재생성 실패 시 Plan B

4. **카테고리 화이트리스트** (3중 방어)
   - 시스템 프롬프트에 "7개 카테고리 외 답변 금지" 명시
   - 응답 파싱 후 카테고리 enum 검증
   - 검증 실패 시 재생성 → 그래도 실패 시 Plan B

5. **DB 캐시 우선** (검증된 답변)
   - 통계 데이터: 7d 캐시 / 사례 검색 결과: 24h 캐시
   - 검증된 답변 캐시 hit 시 환각 없음

6. **응답에 신뢰도 표시**
   - "💡 이 답변은 X건의 실제 사례를 기반으로 작성되었습니다"
   - 사용자가 환각 가능성 인지 + 신뢰도 ↑

**환각 합격 기준 (4주차 50개 시나리오 테스트)**:
- 환각 발생 < 10% (자기검증 적용 전)
- 자기검증 적용 후 < 3% 목표

### 시스템 프롬프트 분리 (페르소나 영향 분리)

- **Section 1 (Tool 선택)**: 페르소나 없이 기능적 지시만 + 환각 방지 룰
  ```
  "질문에 따라 적절한 Tool을 선택하라"
  "Tool 결과에 없는 정보는 생성하지 마라"
  "근거 없는 수치나 통계를 만들지 마라"
  ```
- **Section 2 (응답 생성)**: 페르소나 적용 + case_id 인용 강제
  ```
  "선배의 조언 톤으로 답변하라"
  "응답 끝에 참조한 case_id를 표시하라 (예: [출처: case_42, case_77])"
  ```
- → Tool 선택 정확도 유지 + 응답 톤 통일

## 3. 추가 위험 요소 결정 사항 (v6.1 정리)

### 가드레일
- **입력 가드레일**: 챗봇 입력 → BANNED_WORDS 필터링 → 차단 시 "부적절한 표현이 포함되어 있어요" 안내
- **출력 가드레일**: LLM 응답 → BANNED_WORDS 필터링 → 차단 시 재생성
- **카테고리 화이트리스트**: 7개 부업 카테고리 외 응답 차단 (사기 부업 추천 방지)

### 개인정보 보호 (PII)
- 챗봇 로그에 PII (실명/연락처) 자동 마스킹
- DB 저장 전 정규식으로 전화번호/이메일/주민번호 마스킹
- 마이페이지 PII 표시 시에도 일부 마스킹 (예: 010-****-1234)

### 모델 버전 호환성
- 환경 변수 `CLAUDE_MODEL`로 분리 (예: `claude-sonnet-4-6`)
- 코드에 모델 ID 하드코딩 X
- Anthropic deprecated 시 `.env` 한 줄만 수정 → 재배포

### 시스템 프롬프트 버전 관리
- `prompts/agent_c_v{N}.md` 파일로 저장
- Git commit으로 변경 이력 관리 (예: `feat(prompt): agent C v2 — 한국어 튜닝`)
- 환경 변수 `PROMPT_VERSION`으로 어느 버전 쓸지 선택

### 테스트 환경 — Mock → Haiku → Sonnet 3단 전략
1. **개발 초기**: Mock 모드 (`USE_MOCK_LLM=true`)
   - LLM 호출 안 함 / 미리 정의된 가짜 응답
   - UI/플로우 개발 시 사용 / 비용 0원
2. **통합 테스트**: Haiku 사용 (`CLAUDE_MODEL_DEV=claude-haiku-4-5`)
   - 실제 LLM 호출하되 Haiku (Sonnet의 1/5 비용)
   - ReAct 동작 검증 / 토큰 폭증해도 비용 적음
3. **운영 배포**: Sonnet 사용 (`CLAUDE_MODEL_PROD=claude-sonnet-4-6`)
   - 실제 운영에만 Sonnet / 정확도 ↑
   - 발표 직전 한 번 더 검증

**추가**: 개발용 별도 API 키 + 일일 한도 $5 설정 (Anthropic 콘솔)

### 타임존
- 일일 한도 리셋: **KST 자정 (00:00)** (UTC 15:00에 cron job)
- 사용자에게 보이는 모든 시각: **KST**
- DB 저장: UTC (글로벌 표준) + 표시할 때 KST 변환
- 로그/모니터링: UTC

### 에이전트 A vs C 흐름 충돌 방지
- 글 작성 중 챗봇 FAB **비활성화** (시각적으로 회색 처리)
- 사용자가 글 작성하다가 챗봇 누르면 → "글 작성을 완료한 뒤 이용해주세요" 안내
